# Nova Poshta — розширення адмінки

Сторінка **Nova Poshta** в адмін-панелі (бічне меню) показує всі ТТН, створені
магазином, з живими статусами, синхронізацією та редагуванням накладних.

## Режими списку

Перемикач біля заголовка:
- **«Замовлення магазину»** (за замовчуванням) — ТТН, прив'язані до замовлень
  (з нашої БД), з редагуванням і Sync.
- **«Всі з кабінету НП»** — усі накладні акаунта за період
  (`InternetDocument.getDocumentList`, `GET /admin/novaposhta/cabinet`),
  включно зі створеними поза магазином. Лише перегляд: ТТН (з трек-лінком),
  отримувач, місто, живий статус, вартість, дата.

## Архітектура

```
Замовлення → fulfillment (provider "novaposhta")
                └─ data: { np_ttn, np_document_ref, np_kind, np_city_ref, … }   ← пишеться при продажу
                └─ metadata: { np_status, np_status_code, np_synced_at, np_audit[] } ← пише розширення

Адмін UI (src/admin/routes/novaposhta/page.tsx)
   │  список / фільтри / sync / bulk sync / редагування (Drawer)
   ▼
Адмін API (src/api/admin/novaposhta/…)  — захищено стандартною admin-автентифікацією Medusa
   ├─ GET  /admin/novaposhta/shipments          список + live-статуси (1 батч-виклик NP на сторінку)
   ├─ POST /admin/novaposhta/shipments/sync     {ids[]} → статуси в metadata + аудит
   └─ POST /admin/novaposhta/shipments/:id      редагування накладної (InternetDocument.update)
   ▼
NovaPoshtaClient (src/modules/fulfillment-novaposhta/client.ts)
   ├─ trackDocuments()  TrackingDocument.getStatusDocuments, батчі ≤100, ретраї з backoff
   └─ updateWaybill()   той самий білдер пейлоада, що й створення, + Ref
```

## Як відправлення прив'язані до замовлень

**Жодного скрапінгу кабінету НП.** Провайдер fulfillment при створенні ТТН
записує `np_ttn` і `np_document_ref` у `fulfillment.data`. Список в адмінці
будується З НАШОЇ БАЗИ (замовлення → fulfillments з `np_ttn`), тому особисті
посилки на тому ж акаунті НП **не можуть** з'явитися за построєнням.

Додатково (адитивно, нічого в checkout не змінює): створення тепер також
зберігає `np_kind`/`np_city_ref`/`np_warehouse_ref`/… у `fulfillment.data`,
щоб редагування могло відбудувати повний пейлоад `InternetDocument.update`.
Для старих fulfillment'ів ці поля читаються з shipping method — працює й без
міграції. **Схема БД не змінювалась, міграцій немає** (усе в наявних JSONB
`data`/`metadata`).

## Редагування

НП дозволяє правити накладну **до прийому посилки у відділенні**; далі API
повертає помилку — вона показується адміну як є. Поля: вага, опис вантажу,
оголошена вартість, телефон отримувача, платник (Sender/Recipient), спосіб
оплати НП (Cash/NonCash). Валідація і на клієнті, і на сервері
(`validateEdit`); невідомі поля відкидаються і в НП не потрапляють.

Кожне редагування і кожен sync пишуться в `fulfillment.metadata.np_audit`
(останні 20 записів: хто, коли, які поля) та в лог сервера.

## Кольори статусів

Бейджі статусів (`NpStatusBadge`) використовують спільний з вкладкою Analytics →
Логістика модуль `../../lib/np-status-badge.tsx` (`NpStatusBadge`, `npStatusKey`,
`NP_STATUS_HEX`) — стара локальна функція `statusColor()` прибрана, тепер один
джерело правди для палітри в обох місцях адмінки: невідомо=сірий,
очікує=помаранчевий (тільки Analytics), створено=темно-помаранчевий, в
дорозі=жовтий, прибув=синій (з пульсацією в режимі очікування),
отримано=зелений, видалено=червоний, відмова/повернення=темно-червоний
(відрізняється від видалено).

## Конфігурація

| Змінна | Значення |
|---|---|
| `NOVAPOSHTA_API_KEY` | уже існує; читається лише на сервері, у фронтенд/логи не потрапляє |
| `NP_ADMIN_EXTENSION` | feature flag: `false`/`0`/`off` → роути віддають 404, сторінка показує підказку. За замовчуванням **увімкнено**. Вимикається без відкату коду: змінити env + `pm2 restart` |

## Стійкість

- Live-статуси — один батч-виклик на сторінку (≤100 ТТН/виклик — ліміт НП).
- Ретраї з експоненційним backoff (300мс → 900мс) на транзієнтні збої.
- Якщо НП лежить — список НЕ ламається: показуються збережені статуси з
  `metadata` + позначка «NP недоступна».
- Ключ API ніколи не логуються; логуються моделі/методи і ТТН.

## Тести

- `tests/unit/novaposhta-admin.spec.ts` — мапінг рядків, фільтри, валідація
  редагування, аудит, feature flag, ретраї, злиття трекінгу (24 тести).
- `tests/unit/novaposhta-tracking.spec.ts` — trackDocuments проти мокнутого
  NP API: форма запиту, батчинг >100, дедуплікація, мапінг, помилки (4 тести).
- Запуск: `npx vitest run tests/unit` з `apps/backend`.

Наскрізна перевірка редагування можлива лише з живою редагованою накладною
(до прийому у відділенні) — див. чекліст ручного QA нижче.

## Відкат / вимкнення

1. Миттєво: `NP_ADMIN_EXTENSION=false` + `pm2 restart` (код не чіпається).
2. Повний відкат коду безпечний: розширення нічого не змінює у створенні
   відправлень, дані в `metadata` — необов'язкові.
